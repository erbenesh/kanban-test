# Как вести разработку с агентами

Основной агент в чате пишет код и решает, кого подключить. Специалисты лежат в `.cursor/agents/` и видят одни и те же правила из `.cursor/rules/`. Вызывать всех четверых на каждую правку не нужно: каждый запускается только по своему поводу, обычно по одному.

## Правила проекта

| Файл | Когда попадает в контекст | О чём говорит |
| --- | --- | --- |
| `.cursor/rules/project.mdc` | В каждом чате | Стек, каталоги, команды, кого вызывать |
| `.cursor/rules/architecture.mdc` | Когда в контексте файлы `src/**/*.ts` и `src/**/*.tsx` | Куда класть правило доски, состояние и UI |
| `.cursor/rules/code-quality.mdc` | На тех же исходниках | Типы, производные данные, дубли |
| `.cursor/rules/testing.mdc` | Когда в контексте `*.test.ts` или `*.test.tsx` | Какие сценарии писать и какие команды запускать |

Правило можно подключить вручную, написав в чате `@project`, `@architecture`, `@code-quality` или `@testing`.

## Агенты

### architect

Разбирает требование до кода: куда положить состояние, функции и компоненты, какой вариант будет мешать поддержке. Файлы не меняет.

Вызов: `/architect предложи, где хранить перенос карточки между колонками`.

Нужен перед новой моделью состояния, каталогом или потоком данных. Не нужен для текста кнопки или одного отступа.

### code-reviewer

Ищет ошибки поведения, дыры в типах, нарушение границ модулей и лишнюю сложность. Сам правки не вносит. Сначала сообщает то, что ломает поведение.

Вызов: `/code-reviewer проверь перенос карточки`.

Нужен после законченного изменения поведения. Не нужен для опечатки.

### test-engineer

Составляет сценарии, пишет unit-тесты и запускает `npm test`. Может менять только тестовые файлы. Если падает реализация, описывает дефект и останавливается.

Вызов: `/test-engineer покрой moveTask, включая пустую колонку и неизвестный id`.

Нужен, когда появляется или меняется правило доски, reducer или формат данных.

### ui-reviewer

Сравнивает готовый экран с макетом Figma и с тем, что видно во встроенном браузере Cursor. Код не меняет. Отдельный browser MCP не используется: браузер уже встроен в Cursor.

Вызов: `/ui-reviewer сверь экран доски с этим фреймом Figma: <ссылка>`.

Нужен, когда интерфейс уже открывается. Без ссылки на макет агент прямо пишет, что сверка с Figma недоступна.

## Figma MCP

В `.cursor/mcp.json` подключён официальный удалённый сервер, без локальной команды и без API-ключа:

```json
{
  "mcpServers": {
    "figma": {
      "url": "https://mcp.figma.com/mcp"
    }
  }
}
```

Авторизация делается вручную, потому что сервер входит в аккаунт Figma через OAuth:

1. Откройте Command Palette (`Ctrl+Shift+P`) и выберите Cursor Settings.
2. Перейдите в Tools & MCP.
3. У сервера `figma` нажмите Connect, затем Allow access.
4. На плане Organization или Enterprise может понадобиться подтверждение администратора Figma. После одобрения завершите доступ из уведомления.

Пока Connect не нажат, инструменты Figma в чате не появляются. Context7 в этот файл намеренно не добавлен.

Официальная документация также предлагает плагин командой `/add-plugin figma`. Он ставит тот же сервер и дополнительно навыки Figma. Для этого репозитория достаточно `mcp.json`; плагин ставьте отдельно, только если нужны эти навыки.

## Цикл одной функциональности

1. Зафиксировать наблюдаемое поведение: что видит пользователь и какие данные меняются.
2. Если меняется состояние, каталог или поток данных — `/architect`. Иначе этот шаг пропустить.
3. Основной агент реализует решение в существующих границах.
4. Если менялась бизнес-логика — `/test-engineer`. Он добавляет тесты и запускает `npm test`.
5. `/code-reviewer` смотрит реализацию. Критичные замечания исправляет основной агент, затем снова запускает затронутые тесты.
6. Если менялся экран — `/ui-reviewer` после того, как страница открывается через `npm start`.
7. Основной агент запускает `npm run build` и завершает задачу только после успешной сборки.

Шаги 4–6 не запускать одновременно: ревьюер должен видеть уже написанные тесты, а UI-ревьюер — уже собранный экран.
